- Found and fixed two `NameError` bugs in `auth_service.py` — missing imports for

- Verified requirements/requirements-dev pins by installing into a **completely fresh
  venv** (not the one used for development) and re-running the full test suite against
  it — this catches "works on my venv" drift.

  excludes `hashed_password` by construction, verified in the test).
- Also found and removed leftover duplicate/conflicting files from earlier iteration in
  this build session (a second `PasswordResetToken` model definition, a redundant older
  `test_auth_flow.py`) — reconciled rather than assumed consistent.

### Design decisions
- **Argon2** for password hashing (via passlib) — OWASP's current recommended default.
- **Refresh token rotation**: every `/refresh` call revokes the old session and issues a
  new refresh token. A stolen refresh token used after the legitimate client has already
  rotated it will fail — this bounds the exposure window compared to a static refresh
  token, at the cost of needing this behavior documented for API consumers (don't cache
  the old refresh token after calling `/refresh`).
- **Same generic error for "no such user" and "wrong password"** on login, and **logout
  silently no-ops** on an already-invalid token — both deliberate to avoid leaking
  account existence / token validity to a prober.
- **No password composition rules** (must-have-symbol, etc.) — only a length minimum (10
  chars). This follows NIST SP 800-63B guidance that length matters more than forced
  complexity, which tends to push users toward predictable patterns.

### Known limitation (flagged, not hidden)
- Email verification (`is_email_verified` field exists on the model) is **not enforced**
  — registration succeeds without it, and no email-sending infrastructure exists yet to
  actually deliver a verification link. Tracked as a real gap, not silently shipped as done.
- Password reset **is implemented and tested** (single-use, 1-hour-expiry token, generic
  202 response regardless of account existence, all sessions revoked on reset) — but the
  raw token is only logged server-side, not emailed, since there's no email delivery
  integration yet. This must be replaced before production use; see the TODO in
  `app/api/auth.py::password_reset_request`.
- Rate limiting on `/login` and `/register` (brute-force protection) is **not
  implemented yet** — Redis is provisioned in docker-compose but not yet wired into the
  auth flow. This is a real gap for a production auth system and should be treated as a
  blocker before deployment, not deferred indefinitely.
- Refresh/reset token lookups use an indexed hash comparison (`refresh_token_hash` /
  `token_hash` are unique-indexed columns), so this is O(1) via the index, not a scan —
  correcting an earlier draft of this note that assumed otherwise.

## Frontend/backend integration audit (this session)

A separately-built Next.js frontend was uploaded for integration. It had never
actually been run against the FastAPI backend. Real, verified bugs found and fixed:

- **No CORS middleware on the API at all.** Every browser request from the frontend's
  origin would have been blocked before reaching any route. This is the single biggest
  reason the two halves had never worked together — added `CORSMiddleware` + a
  `CORS_ALLOWED_ORIGINS` setting, verified with a real OPTIONS preflight request.
- `apiClient.refreshToken()` / `.logout()` sent the token as an `Authorization` header;
  the backend expects it in the JSON request body (`RefreshRequest`/`LogoutRequest`).
  Fixed and verified with a real curl round-trip.
- `passwordResetConfirm` sent field `reset_token`; backend expects `token`. Fixed.
- Register/login pages checked for `data.user_id` / `data.email`; the backend's actual
  response shapes are `UserResponse.id` (register) and a token-only `TokenResponse`
  with no user fields at all (login). Login now correctly calls `/me` after
  authenticating rather than trusting client input or a nonexistent response field.
- Dashboard's logout handler passed the **access** token where the backend needs the
  **refresh** token to revoke the session — silently would have failed to log anyone
  out server-side.
- Client-side password validation (≥8 chars) was weaker than the backend's actual rule
  (≥10 chars, not purely alphabetic/numeric) — fixed to match, avoiding a confusing
  pass-then-fail user experience.
- `@heroicons/react` is imported by three components but was missing from
  `package.json` entirely — `npm install` would resolve, but the build would fail the
  moment those components were touched. Added.
- `tsconfig.json` had `"ignoreDeprecations": "6.0"`, which is not a valid value for the
  installed TypeScript version (5.9) — this option only ever accepts the *previous*
  major version as a string, and the invalid value hard-failed `next build` outright
  before any real type-checking even ran. Removed.
- `/auth/forgot-password` was linked from the login page but the page didn't exist —
  added it. Its "confirm" step (entering a token + new password) is *not* built yet,
  because per SECURITY.md the reset token is currently only logged server-side, not
  emailed — building a confirm UI with no way to receive the token would be a fake
  feature, not a real one. Tracked as a dependency on real email delivery.
- `package.json` listed `@supabase/supabase-js` and `axios` as dependencies, but
  neither is used anywhere in the actual code, and `.env.example` implied a Supabase
  integration that doesn't exist. Removed the unused deps and misleading env vars
  rather than leave the app's real dependencies ambiguous.

**Verified together, live:** register → login → `/me` → logout, over real HTTP, with
CORS headers present, using exactly the request/response shapes the fixed frontend
code now sends and expects. `next build` also verified to actually succeed (it did
not, before these fixes) — all 6 routes compile and type-check.

### Security incident noted during this audit

The uploaded archive contained a live `.env` file with a real Supabase
`SUPABASE_SECRET_KEY` (service-role key). This was flagged immediately and the person
was advised to rotate it. This repository's own `.gitignore` excludes `.env`, but that
only helps if the file is never zipped/shared outside git in the first place — worth
remembering that `.gitignore` doesn't protect files handed over by other means.

## Architecture change: Supabase Auth replaces FastAPI auth (this session)

At the person's request, the frontend now uses **Supabase Auth directly** via
`@supabase/ssr` (browser client, server client, and middleware) instead of the FastAPI
`/api/v1/auth/*` endpoints built in Phase 5.

### What changed
- `apps/web/lib/supabase/{client,server}.ts` — new Supabase client helpers
- `apps/web/middleware.ts` — refreshes the session cookie on every request and
  redirects unauthenticated requests away from `/dashboard`
- Login/register/forgot-password rewritten to call `supabase.auth.*` directly
- New `/auth/reset-password` page — this is now a *real* feature (Supabase actually
  sends the email), unlike the FastAPI version where the reset token was only logged
  server-side with no delivery mechanism
- `/dashboard` converted to a server component reading the Supabase session, with
  interactivity (logout) split into a small client component
- Removed: `lib/auth-store.ts` (zustand), `lib/api-client.ts`, the `zustand` dependency

### Verified
- `next build` succeeds with placeholder Supabase credentials — all 7 routes compile,
  `/dashboard` correctly resolves as a dynamic (server-rendered) route, middleware
  bundle builds without error.

### NOT verified (real limitation, not glossed over)
- I do not have this project's actual Supabase URL/anon key, so **no runtime
  authentication has been tested against a real Supabase project** — unlike the
  FastAPI Phase 5 work, which was tested against a live database end-to-end. Before
  trusting this in production: set real `NEXT_PUBLIC_SUPABASE_URL` /
  `NEXT_PUBLIC_SUPABASE_ANON_KEY` in `.env.local`, and manually verify register → email
  confirm (if enabled) → login → dashboard → logout → forgot password → reset password.
- Whether Supabase's "Confirm email" setting is on or off changes register's behavior
  (`data.session` is null if confirmation is required) — the code handles both cases,
  but which one applies to this project needs to be confirmed in the Supabase dashboard
  (Authentication → Providers → Email).
- The `redirectTo` URL in `resetPasswordForEmail` must be added to Supabase's allowed
  redirect URLs list (Authentication → URL Configuration) or the reset link will fail —
  this is a Supabase-dashboard configuration step, not something fixable in code.

### Architectural consequence (important, not cosmetic)
The Phase 4/5 Postgres `users`/`sessions`/`password_reset_tokens` tables and the
FastAPI `/api/v1/auth/*` endpoints are now **dead for authentication purposes**. They
still exist in `apps/api/` and their tests still pass, but nothing in the frontend
calls them anymore. Two paths forward, not decided yet:

1. **Keep FastAPI only for non-auth features** (RAG, search, document Q&A) and have it
   verify Supabase-issued JWTs on incoming requests (Supabase can expose a JWKS/JWT
   secret for this) rather than issuing its own tokens. This means every table with a
   `user_id` FK (conversations, messages, user_documents, etc.) should reference the
   Supabase user's UUID, not a row in our own `users` table.
2. **Drop the FastAPI users/sessions/auth code entirely** and rebuild remaining
   features as Supabase Edge Functions / Postgres RLS policies instead of a separate
   Python backend.

This needs an explicit decision before Phase 6+ (source ingestion, RAG) is built,
since the data model depends on which identity system is authoritative. Flagging this
now rather than silently picking one.
