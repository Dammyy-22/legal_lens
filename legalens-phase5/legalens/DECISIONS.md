### Design decisions
- **Argon2** for password hashing (via passlib) — OWASP's current recommended default.
- **Refresh token rotation**: every `/refresh` call revokes the old session and issues a
  new refresh token. A stolen refresh token used after the legitimate client has already
  rotated it will fail — this bounds the exposure window compared to a static refresh
  token, at the cost of needing this behavior documented for API consumers (don't cache
  the old refresh token after calling `/refresh`).
- **Same generic error for "no such user" and "wrong password"** on login, and **logout
  silently no-ops** on an already-invalid token — both deliberate to avoid leaking
  account existence / token validity to a prober.
- **No password composition rules** (must-have-symbol, etc.) — only a length minimum (10
  chars). This follows NIST SP 800-63B guidance that length matters more than forced
  complexity, which tends to push users toward predictable patterns.

### Known limitation (flagged, not hidden)
- Email verification (`is_email_verified` field exists on the model) is **not enforced**
  — registration succeeds without it, and no email-sending infrastructure exists yet to
  actually deliver a verification link. Tracked as a real gap, not silently shipped as done.
- Password reset **is implemented and tested** (single-use, 1-hour-expiry token, generic
  202 response regardless of account existence, all sessions revoked on reset) — but the
  raw token is only logged server-side, not emailed, since there's no email delivery
  integration yet. This must be replaced before production use; see the TODO in
  `app/api/auth.py::password_reset_request`.
- Rate limiting on `/login` and `/register` (brute-force protection) is **not
  implemented yet** — Redis is provisioned in docker-compose but not yet wired into the
  auth flow. This is a real gap for a production auth system and should be treated as a
  blocker before deployment, not deferred indefinitely.
- Refresh/reset token lookups use an indexed hash comparison (`refresh_token_hash` /
  `token_hash` are unique-indexed columns), so this is O(1) via the index, not a scan —
  correcting an earlier draft of this note that assumed otherwise.
